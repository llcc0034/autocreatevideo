# API 与项目文档规范

## 适用范围

涉及本地 API、外部接口依赖、README、功能基线、架构、数据模型、配置、任务、指标、运维、安全或优化计划文档时，必须使用本规范。

## 按任务加载

先读取本节，再完整读取下表命中的章节。整体文档架构治理、批量收敛多类文档或同时调整 API 与多数项目文档时读取全文。

| 任务范围 | 必读章节 |
| --- | --- |
| 新增、删除或修改本地 API | 文档权威入口；API 文档统一模板；文档与实现同步 |
| 接入或修改外部 API | 文档权威入口；API 文档统一模板；文档与实现同步 |
| 建设、维护或迁移可复用知识库 | 文档权威入口；总体文档格式；文档架构；文档与实现同步；只有知识条目涉及接口时补读“API 文档统一模板” |
| 修改、创建或审查目标项目 README | 文档权威入口；README 与知识库创建边界；总体文档格式；文档架构；文档与实现同步 |
| 新增或调整固定场景规范包 | README 与知识库创建边界；总体文档格式；文档与实现同步 |
| 修改功能基线、架构、数据模型、配置、任务、指标、运维或安全文档 | 总体文档格式；常见文档的最低结构；文档与实现同步 |
| 新建、整理或迁移 `docs/` | 文档权威入口；总体文档格式；常见文档的最低结构；文档架构；文档与实现同步 |
| 优化计划或当前事实与方案分离 | 总体文档格式；文档架构；文档与实现同步 |

## 文档权威入口

- 项目正式 API 统一维护在 `docs/api.md` 或同等职责的唯一文档中，不长期散落在 README、临时 Markdown 或代码注释里。
- 目标业务项目实际依赖的外部系统接口统一维护在 `docs/external-apis.md` 或同等职责文档中，记录用途、请求、响应、鉴权、限制、代码入口、本地落地、失败处理和验证状态。
- 面向多个项目复用的结构化知识库使用独立知识域索引，例如 `knowledge/<domain>/README.md`，并按稳定 ID 一条目一文件维护机器可读元数据和正文；它不能替代目标项目自己的正式依赖清单。
- 从单文件汇总迁移为结构化知识库后，应删除旧汇总、临时导入文件和重复条目，并由检查脚本阻止旧入口重新出现，不保留双份文档兼容。
- README 只承担项目定位、权威启动入口、主要页面或 API 入口和文档导航，不承载完整接口清单或第二套运维说明。
- 临时验证文件、一次性调试说明和个人笔记在内容迁入权威文档后应删除。
- 外部知识库、Skill 或跨项目参考可以作为信息来源，但目标项目仍须记录自己实际使用的接口、代码入口、本地落地和验证状态。
- 新增、删除或调整接口时，同步更新接口文档、功能基线、配置说明、数据模型和任务文档；页面调用变化还要同步页面入口和提示。
- 外部接口响应不得直接由业务页面实时消费；应先进入本地标准化事实、快照、事件、分析结果或文件 manifest。
- 未建立 `README.md`、`knowledge/` 或某份推荐文档本身不是错误；不得只因规范包中提到这些路径就生成空目录、占位索引、空标准文件或模板化内容。

## README 与知识库创建边界

- 场景规范包不交付也不覆盖目标项目 `README.md`、`knowledge/` 或真实 `.env`；安装、升级和直接复制规范包不得修改这些内容。
- 发现 README 缺失、占位或过期时，先检查依赖与锁文件、源码入口、服务管理脚本、容器配置、Schema、页面路由、API、测试、CI 和现有 `docs/`，再说明问题和证据。
- 只有用户明确要求、正在执行项目初始化或文档治理，或当前改动直接改变正式启动、使用、页面、API 或文档入口时，才能创建或修改 README；不得因为应用了规范包而自动生成。
- 已有 README 中仍然正确的定位、业务背景、使用方式、版本约束和外部契约应保留；过期命令、旧路径、失效链接、重复说明和模板占位应删除或更新。
- 触发 README 创建或修改后，只能描述已有代码、已声明命令和可验证入口；优化计划和未实现能力进入规划文档，不写成当前能力，也不写模板内部的场景 ID、构建方式或完整规则。
- 未建立 `knowledge/` 是合法状态。只有项目本身以跨项目复用知识为交付物、存在明确复用需求和真实条目，或用户明确要求时才能创建；普通项目接口依赖继续写入 `docs/api.md` 或 `docs/external-apis.md`。
- 不创建空知识库、占位索引或只有目录说明的知识条目，不从规范来源仓库复制知识正文、认证信息、内部地址、探测结果或真实 `.env`。

目标 README 最低应包含：

| 内容 | 要求 |
| --- | --- |
| 项目名称与定位 | 说明解决的问题、主要用户或交付物，不使用模板通用介绍 |
| 当前状态与能力边界 | 区分已实现、待确认、计划项和不承担职责 |
| 快速启动或使用方式 | 只引用一个权威入口，写明必要环境、依赖和最小步骤 |
| 主要入口 | 按项目类型列出页面、API、服务、CLI、库导出或文档入口 |
| 文档导航 | 链接功能基线、架构、数据模型、API、运维等实际存在的正式文档 |

- 可运行项目的快速启动必须与服务管理脚本一致；库、SDK、CLI、数据任务和文档模板项目可使用安装、调用、执行或应用模板方式替代服务启动。
- README 不保存密钥、真实敏感配置、完整 API 清单、详细 Schema、长篇运维步骤或第二套专项规范，只提供必要摘要和权威链接。
- 无法从当前环境验证的命令、URL、端口和外部依赖应明确标记待确认及原因，不得把推测写成可用事实。
- 更新后根据目标仓库代码、配置、页面、Schema 和测试核对内容真实性；无法验证的内容保留明确的待确认原因。

## API 文档统一模板

- API 文档必须使用统一结构，不能有的接口只有用途、有的只有请求体、有的只有响应示例。
- 平台本地 API 每个接口至少包含：接口卡片、请求、响应、错误处理、权限与安全、数据口径或副作用、调用入口、验证状态。
- 外部接口每个接口至少包含：接口卡片、请求、响应、本项目使用、失败处理、验证状态；批量、分页、限流、签名和文件上传需单独说明。

### 接口卡片

至少写明：

- 用途、Method、Path 或 URL。
- 鉴权方式和对应配置项。
- 代码入口、页面或任务入口。
- 读取或写入位置、数据落地位置。
- 当前状态，例如已使用、计划接入、停用或待验证。

### 请求

至少写明：

- Header、Path、Query 和 Body 字段。
- 字段类型、是否必填、默认值、枚举、空值语义和单位。
- 分页、批量、时间范围、排序和限流约束。
- 能体现真实结构但不包含敏感信息的最小可用示例。

### 响应

至少写明：

- 成功响应结构和核心字段含义。
- 列表、分页、游标、文件或异步任务结构。
- 空数据、部分数据、字段缺失和数据时间语义。
- 关键响应示例；不能只贴示例而不解释字段。

### 错误与失败处理

至少写明：

- HTTP 状态码、业务错误码和参数校验失败。
- 外部依赖失败、超时、限流、权限不足、空数据和核心字段缺失。
- 部分成功、幂等冲突、重试、补偿和是否保留上一成功事实。
- 页面或调用方应如何展示、重试或进入任务历史查看。

### 权限、安全与审计

至少写明：

- 登录态、角色、管理员权限和数据范围。
- 密钥来源、脱敏规则和是否允许页面直接触发。
- 是否记录审计，以及操作人、对象、参数摘要、结果和错误。
- 高风险、覆盖、删除、重跑或终端操作的确认要求。

### 数据口径与副作用

至少写明：

- 读取哪些表、快照、派生结果或文件 manifest。
- 写入哪些表或文件，是否覆盖当前事实。
- 是否触发同步、派生分析、通知、缓存失效或外部访问。
- 时间范围、筛选、排序、分页、统计和导出口径。

### 调用入口与验证状态

- 写明对应页面、按钮、定时任务、手动任务和内部调用方；业务操作没有页面入口时必须说明合理原因。
- 写明已验证的调用方式、样例范围、测试或手工结论以及未验证风险。
- 未验证接口不得描述为已确认；摘要清单不能替代每个接口的完整说明。

## 总体文档格式

- 正式文档开头说明职责、适用范围和当前状态，使读者能判断它描述当前事实、目标方案、优化计划还是历史记录。
- 同一类型文档使用相同结构；标题应明确、稳定、可检索，不使用临时或只有作者理解的名称。
- 内容按“结论或当前口径在前，细节和补充在后”组织。当前主路径文档不混入大段未落地方案和迁移回忆。
- 每份文档说明与代码、页面、任务、配置、数据表或外部系统的对应关系；只有业务想法但没有落点的内容进入优化计划。
- 字段、配置、指标、接口、任务和表结构优先使用表格，至少包含名称、含义、来源、类型或取值、使用方和更新规则。
- 状态流转、数据流、依赖关系和 ER 图使用可维护文本图或 Mermaid，并保持图和说明一致。
- 示例只能解释结构，不得伪装真实运行数据；密钥、Token、密码、账号、真实敏感 IP 和其他秘密必须脱敏。
- “已实现”“计划做”“暂不做”“观察中”必须明确区分；未实现、未运行或未验证内容不得写为当前能力。
- 当前文档不保留旧逻辑解释、迁移过程回忆和临时兼容说明；确需追溯时进入优化台账或变更记录并标明状态。
- 文档变更后检查链接、文件路径、页面入口、接口路径、表名和配置项是否存在，直接修正或删除失效引用。

## 常见文档的最低结构

| 文档类型 | 最低结构 |
| --- | --- |
| 项目入口文档 | 项目定位、快速启动、服务管理、主要页面或 API、文档导航、必要环境 |
| 文档索引 | 文档分组、职责、阅读顺序、当前事实与计划边界 |
| 功能基线 | 模块目标、页面入口、已实现能力、数据来源、操作入口、能力边界、不承担职责 |
| 架构文档 | 当前架构图、模块职责、调用链路、数据流、外部依赖、关键约束 |
| 数据模型 | 权威 Schema、ER 图、存储选型、冷热分层、表职责、字段上限、payload、索引、来源、读取方、保留与归档 |
| 配置中心 | 名称、用途、默认值、范围、保存位置、生效时机、读取方、影响、异常处理 |
| API 文档 | 接口卡片、请求、响应、错误、权限、安全、口径、副作用、入口、验证 |
| 外部接口 | 接口卡片、请求、响应、本项目使用、失败、验证、本地落地 |
| 任务与运维 | 名称、触发方式、页面入口、参数、步骤、写入、失败、重跑或回滚、日志 |
| 指标与报表 | 指标定义、统计口径、来源、范围、筛选、聚合、下钻、导出 |
| 安全文档 | 权限、密钥、敏感数据、审计、高风险确认、外部访问边界 |
| 优化计划 | 问题、当前现状、目标方案、步骤、影响、验收、状态、暂不做事项 |

## 文档架构

- 本节只定义文档职责和 `docs/` 结构；源码、测试、迁移、脚本、生成物和运行期目录由 `.agents/project-structure.md` 统一管理，不能在文档规范中再维护第二套项目目录口径。
- 接手项目时先确认文档索引、功能基线、数据模型或 Schema、运行部署说明、任务或运维入口是否存在且与代码一致。
- 文档缺失、混乱或指向旧主路径时，应在较大功能开发或重构前建立最小可用架构；不能凭空设计未实现能力。
- 文档目录区分当前事实与优化计划。当前主路径、接口、页面、数据模型、任务入口和指标口径进入主文档；方案、迁移评估、观察项和路线进入独立规划目录。
- 优化台账记录已落地、计划做、暂不做或观察中，并写明当前记录、触发条件和后续动作。
- 主文档只保留已落地事实、必要约束和规划台账链接，不长期混入迁移过程和过期口径。
- 调整文档结构后检查旧链接、旧路径和重复文档，确保一个权威索引指向当前主路径。
- 当项目本身交付可复用知识库时，`knowledge/` 与目标项目的 `docs/` 分工维护：前者保存跨项目稳定知识和工具，后者保存本项目实际依赖与落地事实；同一接口契约不在两个位置复制完整正文。

推荐结构可按技术栈裁剪，但职责不能混用：

```text
README.md
AGENTS.md
.agents/
docs/
  README.md
  feature-baseline.md
  architecture.md
  data-model.md
  config-center.md
  api.md
  external-apis.md
  operations.md
  tasks.md
  metrics-and-reports.md
  security.md
  optimization/
    README.md
    <topic-plan>.md
```

| 文档 | 适用条件 | 职责 |
| --- | --- | --- |
| `README.md` | 已存在，或满足本文件创建条件 | 项目定位、快速启动或使用方式、主要入口和必要文档导航 |
| `AGENTS.md` | 使用本规范包 | 项目事实、全局硬约束和专项规则路由 |
| `docs/README.md` | 已建立 `docs/` 且存在多份正式文档 | 文档索引、职责和阅读顺序 |
| `feature-baseline.md` | 产品型应用、多模块平台或 README 已无法清晰承载功能边界 | 当前功能、页面入口和能力边界 |
| `architecture.md` | 中大型项目 | 当前架构、模块、数据流和外部依赖 |
| `data-model.md` | 涉及持久化 | 权威 Schema、字段、存储、索引和数据流 |
| `config-center.md` | 存在运行期配置 | 配置结构、默认值、保存、生效范围和读取方 |
| `api.md` | 有本地 API | 当前正式 API、请求响应、错误和调用边界 |
| `external-apis.md` | 依赖外部系统 | 外部接口、鉴权、限制、本地落地和失败处理 |
| `operations.md` | 有可运行服务 | 启停、日志、配置、发布和回滚 |
| `tasks.md` | 有定时或手动任务 | 任务中心、定时、补跑和正式触发入口 |
| `metrics-and-reports.md` | 有指标报表 | 定义、口径、来源、趋势、下钻和导出 |
| `security.md` | 涉及权限或密钥 | 权限、密钥、审计和安全边界 |
| `optimization/README.md` | 存在计划项 | 优化、迁移、评估和暂不做事项台账 |

最小文档集合按项目形态和已实现职责确定，不按标准目录机械创建空文件：使用本规范包时保留 `AGENTS.md` 与其受管专项；README 仅在已有或满足本文件创建条件时维护；只有建立多份正式文档时才创建 `docs/README.md`；只有产品能力超出 README 承载范围时才创建功能基线；数据模型、运行、配置、API、任务、安全和优化文档均按对应职责实际存在时创建。小型 CLI、SDK、脚本、静态站点或早期原型在确需 README 时可以由其同时承担入口、能力边界和文档导航；没有实际优化项时不创建空优化台账。

## 文档与实现同步

- 功能入口、数据来源、指标、报表、任务、配置或存储口径变化时，同步更新对应文档。
- 文档只描述当前代码主路径，不继续描述已删除入口、旁路脚本或临时止血方案。
- 保留开发工具、Schema 变更脚本或一次性修复工具时，文档明确边界、用途、风险和禁止作为业务日常入口。
- 文档更新不能替代实现验证；没有代码、接口、数据或运行证据时，应标记为方案或未验证状态。
