# 数据、后端与运行期配置规范

## 适用范围

涉及数据库、Schema、字段、索引、文件或对象存储、缓存、数据同步、任务状态、配置中心、通知中心、数据修复、报表事实和容量管理时，必须使用本规范。

## 按任务加载

先读取本节，再完整读取下表命中的章节。任务跨多个范围时读取章节并集；涉及整体数据架构、主存储迁移或同时调整多数职责时读取全文。

| 任务范围 | 必读章节 |
| --- | --- |
| 新表、字段、关系、Schema、索引或查询模型 | 主存储与事实来源；数据库与文件存储选型；字段、行宽与 Payload；Schema、主键与索引；可维护性监控 |
| 文件或对象存储、附件、快照、归档 | 主存储与事实来源；数据库与文件存储选型；文件 manifest；热、温、冷数据；可维护性监控 |
| 列表、分页、聚合、报表或性能优化 | 查询与响应性能；Schema、主键与索引；缓存；涉及大字段时补读“字段、行宽与 Payload” |
| 缓存设计或失效问题 | 缓存；查询与响应性能；主存储与事实来源 |
| 全量、增量、补数、重算或归档同步 | 主存储与事实来源；文件 manifest（涉及原始文件时）；数据同步与一致性；同步频率与容量；缓存 |
| 配置中心或运行期策略 | 配置中心；问题修复与历史脏数据（涉及错误配置或历史口径时） |
| 通知、催办、升级或 SLA 提醒 | 通知中心；配置中心（规则可运营时） |
| 字段缺失、脏数据、数量异常或修复重算 | 问题修复与历史脏数据；与问题来源对应的存储、Schema、同步或查询章节 |
| 容量、保留、分层、归档或清理 | 热、温、冷数据；文件 manifest；同步频率与容量；可维护性监控 |

## 主存储与事实来源

- 运行期数据必须有明确主存储。页面、API、报表、分析和任务中心读取数据库中的标准化事实，或正式文件存储的元数据与按需内容。
- 本地文件只可作为开发调试输入、临时文件或明确标注的非权威缓存，不得静默参与正式运行口径。
- 配置、任务历史、同步批次、审计记录、通知记录和分析结果等运行期状态必须进入正式存储，不能散落在临时文件中。
- 主存储写入失败必须记录失败并向调用方或页面返回异常，不得写本地文件、内存或旧快照后伪装成功。
- 数据库标准化数据负责页面和计算，原始文件负责追溯和重算；两者不能同时成为当前业务事实的权威来源。

## 数据库与文件存储选型

| 数据场景 | 主存储 | 要求 |
| --- | --- | --- |
| 需要筛选、排序、分页、联表、聚合、唯一性或事务一致性的结构化数据 | 数据库 | 使用有类型字段、关系、约束和索引 |
| 当前状态、任务状态、配置、审计、页面清单、近期明细和高频报表结果 | 数据库 | 使用可维护表结构、版本和保留策略 |
| 原始全量快照、外部响应原文、附件、图片、导出、大日志、终端输出和二进制 | 正式文件或对象存储 | 数据库只保存 manifest、摘要和查询字段 |
| 长期低频追溯的历史证据 | 文件存储 + 数据库 manifest | 通过 manifest 定位和管理生命周期，不扫描目录查询 |

- 不得因建表麻烦或字段可能变化，把稳定读取字段全部塞入 JSON、`payload` 或文件。
- 页面、API、报表或任务需要稳定展示、筛选、排序、聚合、唯一性、状态判定、幂等、关联、审计或单独更新的字段，应拆为正式字段或关联子表。
- 页面普通查询不得扫描文件目录、下载原始快照或实时请求外部系统；高频展示内容必须预先标准化或聚合入库。

## 文件 manifest

每个正式文件对象至少记录：

- 业务主键或快照键。
- 存储后端、bucket 或容器、object key；不得只保存会过期的签名 URL。
- 文件大小、内容类型、checksum、schema 版本。
- 数据来源、任务或批次、创建时间和写入状态。
- 必要的保留期限、归档状态、读取方和恢复方式。

只有文件对象和 manifest 均成功写入并完成校验后，才能将其标记为可用或发布新数据版本。

## 热、温、冷数据

- 数据分层按实际读取频率和查询方式确定，不只按日期判断。
- 首屏、常用筛选、当前状态、待处理记录和近期差异属于热数据，应存储在数据库窄表或针对查询的汇总表中，并具备必要索引。
- 仍需查询但不参与大多数默认页面的近期历史属于温数据，可使用历史表、时间分区、周期汇总或独立分析表；页面不得每次重算完整历史。
- 只用于审计、异常排查、证据追溯或低频重算的原始历史属于冷数据，应优先进入文件存储，数据库保留 manifest、摘要和必要索引字段。
- 每张表和每类文件必须明确粒度、写入方、读取方、数据层级、预计数量级、增长速度、保留时长、归档条件、清理方式和恢复方式。
- 表、快照目录和审计文件不得在没有生命周期策略时无限增长。
- 高频报表无法满足性能目标时，应建立可重算的汇总表或派生事实表，并记录源数据版本、配置 hash、计算时间和完整性状态。

## 字段、行宽与 Payload

- 高频主表保持窄表设计；列表、关联、筛选、排序和汇总使用的普通单字段，UTF-8 序列化后默认不超过 `4 KiB`。
- 新增数据库单字段的应用层序列化结果硬上限为 `64 KiB`。超过该上限的原文、JSON、日志或命令输出必须进入文件存储，或拆为带稳定主键和顺序的子表。
- 不得使用 `LONGTEXT`、`LONGBLOB` 或无上限 JSON 绕过 `64 KiB` 限制。
- 图片、附件、压缩包、二进制快照和 Base64 内容不得直接存入业务数据库；数据库保存 object key、checksum、大小、类型和业务关联。
- 大文本、JSON 或原始响应即使未超过 `64 KiB`，也不得放入默认列表主表或普通查询默认返回；应使用详情表、扩展表或文件存储，由详情接口按需读取。
- `payload` 只保留低频、来源特有、暂无稳定模型或仅用于排查的扩展字段，并记录 `schema_version`、来源、字节大小和必要 checksum；写入时必须校验大小。
- 可重复数组、组件、节点、操作记录和状态流转应使用一对多子表，明确顺序、自然键或唯一性及删除口径，不能在主表 JSON 中无限追加。
- 字段必须明确类型、单位、枚举、空值语义、数据来源、更新规则和时间口径；不得统一使用无语义的 `VARCHAR(255)` 或字符串时间。

## Schema、主键与索引

- 每个项目只有一个权威 Schema 或迁移入口，不得长期保留多套可创建或修改同一结构的脚本。
- 数据结构变更应收敛到明确目录或入口，并区分运行期代码与一次性数据处理工具。
- 业务实体必须有稳定主键；快照键、外部唯一标识、幂等键和业务唯一组合应建立唯一索引，不能只依赖应用层查重。
- 索引必须来自已确认的查询、关联、唯一性或排序需求，不为每个字段预防性建索引。
- 复合索引顺序优先考虑高频等值筛选、权限或业务范围、范围或时间字段、排序字段，并按真实 SQL 和左前缀验证。
- 外键或关联字段、常用时间边界、分页排序键和经常与状态组合的字段按实际 SQL 建索引；低区分度布尔值或枚举单独建索引前必须验证选择性。
- 对采用常见关系型数据库和普通 B-tree 索引的项目，完整字符串默认不超过 `191` 个字符；超长标识使用归一化键、摘要 hash、前缀索引或专用检索方案，并验证碰撞和回表成本。其他数据库按其真实索引能力、编码和限制验证，不机械套用该数字。
- 不对 `TEXT`、`BLOB`、完整 JSON 或原始 `payload` 直接建普通索引。需要查询稳定 JSON 属性时，应拆为正式字段；使用生成列必须有明确数据库能力和性能验证。
- 对关系型数据库中的单张高频写入表，原则上不超过 `8` 个二级索引；超过时必须提供真实 SQL、`EXPLAIN`、索引选择性、写入放大和无法合并的原因。非关系型存储按对应读写放大和索引机制提供等价证据。
- 唯一索引和普通索引使用统一可读前缀，例如 `uk_`、`idx_`；不得在运行期临时建索引。
- 应检查重复索引、前缀重叠索引、未使用索引和慢查询。
- 新增或修改高频查询时必须检查 `EXPLAIN`，确认扫描行数、使用索引、回表、临时表和额外排序；除小型维表或有明确上限的表外，普通页面查询不得默认全表扫描。

## 查询与响应性能

- 普通列表、汇总和详情读取本地数据库、正式分析结果或可追踪缓存；不得在用户等待期间串行访问外部系统或下载冷文件。
- 高频列表 API 的数据库与后端处理 `P95` 目标不超过 `2s`；普通页面首批可见数据不超过 `3s`；复杂报表同步查询不超过 `5s`。
- 预计超过 `5s` 的计算应使用异步任务、汇总表或预计算，不长期占用同步请求。
- 列表查询显式选择所需列，不使用 `SELECT *` 带出大文本、原始 payload 或低频字段；关联详情应批量读取，避免 N+1。
- 普通分页默认每页不超过 `50` 条，单次上限不超过 `200` 条；大数据量深分页使用稳定排序键和游标或 keyset，不使用持续增大的 `OFFSET`。
- 普通列表或详情 JSON 优先控制在 `1 MiB` 以内，不得将超过 `5 MiB` 的 JSON 作为常规同步响应；应分页、拆分详情或生成文件。
- 首屏只加载当前可见视图；隐藏 Tab、大详情、历史记录和原始内容按需加载。
- 筛选选项来自维表、去重结果或缓存，不得每次扫描大事实表。
- 汇总、趋势和分布与明细使用相同过滤口径；重复全量 `COUNT`、相同聚合或展示层重算应收敛为一次查询、汇总表或可失效缓存。
- 导出和大范围明细使用独立任务、分批读取和文件存储，不将全量结果一次性放入浏览器内存。

## 缓存

- 缓存只用于读取优化，不能成为唯一事实来源。业务写入、任务、同步和配置保存必须先成功提交主存储，再更新或失效缓存。
- 缓存键必须包含页面或业务域、查询条件、数据范围、时间粒度、权限或用户范围、配置版本和必要数据版本。
- 每类缓存必须明确 TTL、主动失效时机、最大大小、数据版本和允许的最大陈旧时间；可运营策略进入配置中心，不散落为常量。
- 缓存结果携带 `generated_at`、`source_data_at` 或快照键、完整性状态和必要的 `expires_at`。
- 返回陈旧缓存时页面必须显示数据时间和陈旧原因，不能伪装为刚完成的新查询。
- 查询失败、部分成功、权限不足和不完整同步不得写成正常缓存；为限流缓存失败状态时使用独立状态和短 TTL。
- 高成本查询应按需要使用请求合并、单飞或锁避免缓存击穿，但不得用缓存长期掩盖缺失索引、N+1 或不合理聚合。
- 单实例可使用内存缓存作为非权威优化；多实例使用共享缓存或基于数据版本的一致失效方案。

## 数据同步与一致性

- 外部系统数据先通过正式同步任务进入本地主存储，页面再读取本地数据；页面不得绕过主存储实时消费外部响应。
- 同步任务必须明确属于全量、增量、补数、重算还是归档，不能用含糊逻辑混合多种模式。
- 同步主链路应为：创建任务批次 → 获取数据 → 必要时归档原始文件 → 写入 staging → 完整性校验 → 标准化 → 事务提交或原子切换当前版本 → 生成派生结果 → 标记任务成功 → 失效缓存。
- 不得边拉取边覆盖最后一份成功的当前事实。
- 每次同步记录 `run_id` 或快照键、数据源、源时间范围、开始结束时间、拉取量、有效量、无效量、新增量、更新量、删除或失效量、checksum 或数据版本、配置 hash、状态、错误原因和异常样例。
- 全量同步不得用空结果、部分结果、核心字段缺失或明显低于合理基线的结果覆盖最后成功数据。失败时保留上一成功事实，但任务和页面必须标记同步失败或数据陈旧。
- 增量同步必须持久化水位、cursor 或事件偏移，明确重叠窗口、迟到、乱序、重复、删除或 tombstone 处理，并定期全量对账。
- 同步写入必须幂等，使用业务键、快照键或事件键防重；同一业务范围使用任务锁或并发版本校验，避免相互覆盖。
- 大批量写入使用可配置批次，避免超大事务、长时间锁表和一次占满内存；任务保存检查点并支持不产生重复事实的安全重试。
- 上游快照、核心元数据或配置变化时，依赖的汇总表、派生事实、索引数据和缓存必须通过显式重算或版本切换更新，不能在查询层临时拼接其他来源。
- 主存储事务、派生结果和 manifest 全部就绪后才能发布新数据版本并失效缓存；缓存失效失败必须可重试、可监控。

## 同步频率与容量

- 同步频率由业务最大允许陈旧时间、变化速度、SLA 或通知时效、外部限流、单次数据量、计算成本、数据库压力和存储增长共同决定，不能统一追求高频。
- 活动告警、待处理工单、处理中节点和通知状态等高变化数据，优先事件驱动或分钟级增量；不得按同样频率反复写完整全量快照。
- CMDB 状态、负责人、机房和常规资源属性等可采用小时级或日级同步，并以较低频全量对账纠正漂移。
- 完整硬件清单、外部原文、全量归档和低频历史证据可采用日级、周级或按需同步；原始全量优先文件存储。
- 当前事实刷新频率与原始全量归档频率应分别设计，避免高频页面刷新无限制造重复大文件。
- 调整频率时必须估算每日新增行数、文件数、索引增长、备份时间和保留周期，并同步调整增量模型、分区或归档、汇总压缩和清理策略。
- 高频任务应具备增量水位、重叠窗口、任务锁、退避重试和定期全量校验；低频全量任务优先保证完整性、checksum、可重跑和原子切换。
- 同步周期、允许陈旧时间、对账周期、重试间隔和归档频率属于运行期策略时，应进入任务中心或配置中心并说明默认值、范围、生效时机和容量影响。
- 页面需要更实时的数据时，优先新增轻量增量或事件链路，不让页面直连外部系统，也不通过缩短所有全量任务解决单一页面需求。

## 配置中心

- SLA 阈值、报表口径、任务参数、业务策略、功能开关和可运营规则必须进入一个正式配置入口。面向产品或管理平台且需要运行期运营时优先使用配置中心页面与 API；CLI、SDK、批任务、基础设施和设备项目可使用类型化配置、参数或受控配置文件，但仍只能有一个权威入口。
- 配置项应记录名称、用途、默认值、取值范围、保存位置、生效时机、读取方和变更影响。
- 被两个及以上模块共用的配置应收敛为独立公共配置域，由一个权威配置键和数据对象提供；存在服务 API 或配置页面时只暴露同一入口，不为无界面项目机械创建页面。
- 公共配置收敛后删除旧 Tab、重复字段、旧配置键、隐藏默认值、双写双读和重复读取逻辑。
- `0`、空值和缺省值的特殊语义必须在实际配置入口、API 或文档中说明，不能使用隐藏默认值掩盖缺失配置。
- 配置保存、加载或格式校验失败时必须显式报错并阻止错误配置生效。
- 配置变化影响历史分析时，应区分历史落盘口径与最新配置实时评估口径，不能用新配置静默覆盖历史事实。

## 通知中心

- 出现通知、催办、升级或 SLA 提醒时，应建立一个独立、权威的通知规则与发送历史入口。面向产品或管理平台且存在正式页面时，通知中心与配置中心同级；无界面服务、CLI 或批任务使用正式配置与查询 API、命令或运维入口，不为满足规范机械创建页面。
- 通知中心统一管理场景、触发条件、时点或周期、接收人来源、渠道或机器人、模板、去重、限流、静默、升级、启停和测试发送。
- 每条规则应说明规则名称、适用对象、数据来源、判定条件、时间口径、接收人来源、通知渠道、默认值、取值范围、生效时机和变更影响。
- 存在业务页面时只展示通知状态或跳转入口，不维护第二份规则。
- 收件人能从工单、告警、CMDB 或业务事实确定时，应读取业务负责人，不重复维护负责人映射。
- 通知事件必须有唯一或幂等标识，并记录触发时间、实际收件人、渠道、模板或内容摘要、发送结果、重试次数和错误原因。
- 正式管理页面、查询 API 或任务入口必须支持查询发送结果和历史，不能以短暂 Toast 或散落日志文件作为唯一反馈。
- 渠道密钥、Webhook 和机器人 URL 使用正式密钥存储并脱敏展示，不写入前端、文档、审计正文或发送记录。

## 问题修复与历史脏数据

- 排查时保留异常输入、入库内容、任务记录、错误日志、影响范围和可复现条件，不得为页面短期正常覆盖或删除现场。
- 修复优先落在产生错误数据的源头，确保新增数据正确。
- 历史脏数据通过可审计、可重复执行的数据修复或重算任务处理，并记录范围、版本、执行人、结果和异常。
- 关键字段增加来源或改变口径时，同步检查写入、查询、导出、报表和页面链路。
- 快照、同步和补跑在落库前进行完整性校验；核心字段缺失、详情补全失败或明显降级时应阻止发布，并在任务历史和页面展示问题。
- 派生结果依赖的上游元数据被补全或修正时，应通过显式同步或重算更新，并在任务进度显示影响数量。
- 修复后重新验证任务、源快照、标准化事实、派生结果、查询、导出和页面是否收敛；同一批数据每次重跑仍大幅变化时继续排查差异，不能叠加补偿逻辑。

## 可维护性监控

- 监控表行数、数据量、索引量、单行与 payload 大小分布、慢查询、扫描行数、缓存命中率、同步耗时、同步延迟和失败率。
- 超出设计基线时通过正式任务、迁移或数据模型调整处理。
- 时间分区、分库分表、搜索引擎和专用分析存储只在容量、查询或写入证据表明单库方案不足时引入，不用复杂架构代替基本 Schema、索引和查询优化。
- 字段上限、索引、保留策略、归档任务和数据修复必须同步进入权威 Schema、数据模型文档和运维文档。
