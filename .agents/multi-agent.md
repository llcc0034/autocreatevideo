# 多 Agent 协作规范

## 适用范围

用户明确要求多 Agent、子 Agent、并行代理、角色协作，或任务需要在多个工作树、分支、专业领域之间并行推进时，必须使用本规范。

本规范负责多 Agent 的启用条件、任务拆分、角色边界、写入隔离、信息交接、集成和验收。具体代码、数据、前端、运行环境、API、文档和验证规则仍由根 `AGENTS.md` 及对应专项文件负责。

## 启用条件

- 默认使用单一主 Agent。只有存在两个以上边界清晰、输入与交付明确、依赖可控且并行收益高于协调成本的子任务时，才启用多 Agent。
- 用户明确要求多 Agent 或适用规范、Skill 明确要求委派时，可以启用；不能仅因任务较大就固定创建一整套角色。
- 代码探索、日志分析、文档核对、测试分析、代码审查、产品体验评估等只读或低冲突任务优先并行。
- 单点修改、强顺序依赖、需求口径未确定、修改范围高度重叠或预计协调成本更高时，不启用多 Agent。
- 角色数量按实际任务动态决定；不创建没有独立目标、交付物或验收方式的占位 Agent。

## 主 Agent 职责

- 主 Agent 是当前目标的唯一协调入口，负责确认目标、当前事实、范围、依赖、风险、验收条件和最终决策人。
- 委派前先划分任务依赖；存在共享 API、Schema、配置、业务规则、设计基线或公共组件时，先确定唯一契约，再安排并行实现。
- 为每个子 Agent 明确任务目标、允许范围、禁止范围、输入资料、允许写入的文件或目录、预期交付物、验证要求和前置依赖。
- 持续保留集成、冲突处理和最终验证职责；子 Agent 完成只代表其子任务返回结果，不能直接视为整体目标完成。
- 汇总时核对代码、页面、API、Schema、配置、测试和文档是否仍指向同一主路径，不直接拼接彼此冲突的结论或实现。

## 子 Agent 与角色边界

- 子 Agent 只处理被委派的明确范围；发现跨范围问题时返回证据、影响和建议，不擅自扩大修改范围。
- 产品、项目管理、架构、前端、后端、数据、测试、安全和体验等角色按实际需要选择，不固定要求每次全部创建。
- 项目管理或协调角色负责范围、依赖、状态和验收，不直接覆盖专业角色的已验证事实；专业角色不能自行改变已确认的产品目标和验收口径。
- 测试、审查和体验角色默认先报告问题，不得通过降低断言、隐藏失败、修改展示兜底或改变需求让问题表面通过。
- Skill 用于提供可复用工作流，不代表新的项目权威规则；Skill 与根或专项规范冲突时，以根 `AGENTS.md` 和更接近改动范围的专项规范为先。

## 并行写入与工作树

- 多个 Agent 共用同一代码目录时，同一时间只能有一个写入者；其他 Agent 只能进行只读分析、检查或等待依赖。
- 需要并行写代码时，必须先确认目录是 Git 仓库；确认后每个独立任务使用单独工作树和唯一分支，并明确各自文件、模块和公共契约边界。不是 Git 仓库或无法建立隔离工作树时，继续使用共享目录单写入者，不用复制目录冒充安全隔离。
- 工作树只隔离文件目录，不隔离 Git 历史、端口、数据库、外部服务、密钥和其他运行资源；并行运行前必须检查共享资源冲突和数据污染风险。
- 即使使用不同工作树，多个 Agent 也不得未经协调同时修改同一个权威 Schema、API 契约、公共配置、导航入口、核心类型或协作规范。
- 不将不同分支中的竞争实现同时保留为正式主路径。实验方案必须明确标记，集成前由主 Agent 或用户选择并收敛为一个正式实现。
- 未经用户明确要求，不自动合并到主分支，不删除分支或工作树，也不以重置、强制推送或丢弃其他改动解决冲突。

## 信息交接与监督

- 同一主任务内的子 Agent 通过主 Agent 接收任务和返回结果，避免子 Agent 之间形成未经确认的独立决策链。
- 不同 Codex 任务或工作树默认不共享对话上下文，也不会自动了解彼此进度；必须通过明确的分支、提交、差异、计划记录或交付报告完成交接。
- 项目状态只保留一个权威入口。存在 `PLANS.md`、任务系统或正式计划文档时，由一个明确角色负责维护，其他 Agent 返回状态而不并行改写同一状态文件。
- 每个子任务至少返回：完成内容、修改或检查范围、验证结果、未验证项、发现的问题、依赖和建议的下一步。
- 监督采用明确检查关系，例如范围检查、接口契约检查、代码审查、测试、产品体验验收；不安排所有角色无边界地互相指挥或重复审查。

## 冲突、失败与集成

- 子 Agent 结论冲突时，主 Agent 应回到代码、数据、文档、运行结果和用户确认的验收标准核对，不按多数意见直接决定。
- 子任务失败或受阻时必须保留真实失败状态和证据；主 Agent 可以调整拆分、顺序或责任范围，但不能用其他 Agent 的推测伪装完成。
- 集成前检查分支基线、重叠文件、公共契约、迁移顺序、配置变化和测试依赖，明确合并顺序及冲突处理方案。
- 多个分支分别验证通过不等于集成通过；合并后必须按照 `.agents/verification.md` 对组合结果重新执行受影响范围的验证。
- 最终交付由主 Agent 统一说明已完成、已验证、未验证、失败项、合并状态和剩余风险，并确认没有遗留重复入口、竞争实现或第二事实来源。
