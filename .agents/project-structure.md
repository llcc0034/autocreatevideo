# 项目目录结构规范

## 适用范围

初始化新项目、接手现有项目、识别技术形态、新增应用或服务、移动模块、整理根目录或调整源码、测试、迁移、脚本和运行期目录时，必须使用本规范。

本规范采用“通用底线 + 项目类型档案”。通用底线适用于所有项目；类型档案根据仓库证据自动选择，不用一种源码结构强行覆盖所有技术栈。

本文件选择的是代码交付形态和目录档案；产品或业务场景由目标项目复制的固定场景规范包确定。项目只选择一个主要场景，不能组合多个场景，也不能用“后台管理”“DevOps”等业务名称代替实际技术目录识别。

## 按任务加载

先读取本节和“自动识别与记录”，再按下表读取完整章节或子章节。不需要读取未选中的其他项目类型档案。

| 任务范围 | 必读内容 |
| --- | --- |
| 初次接手、初始化或识别项目类型 | 自动识别与记录；所有项目的通用底线；项目类型档案中命中的一个主档案和必要附加档案 |
| 整理根目录、命名或重复目录 | 通用底线中的“根目录”“命名与职责”；结构调整与迁移 |
| 移动源码、测试或共享模块 | 通用底线中的“命名与职责”“源码、测试和依赖方向”；命中的项目类型档案；结构调整与迁移 |
| 调整 Schema、配置或脚本目录 | 通用底线中的“Schema、配置和脚本”；命中的项目类型档案；结构调整与迁移 |
| 调整生成物、日志、缓存、上传或本地数据库目录 | 通用底线中的“生成物与运行期文件”；结构调整与迁移 |
| 调整文档、容器、部署或 IaC 位置 | 通用底线中的“文档与基础设施”；命中的项目类型档案；结构调整与迁移 |
| 调整可复用知识库、知识域索引或配套工具 | 通用底线中的“根目录”“命名与职责”“Schema、配置和脚本”“文档与基础设施”；文档或规范模板项目；结构调整与迁移 |
| 新增应用、服务或 Monorepo 工作区 | 所有项目的通用底线；命中的项目类型档案；结构调整与迁移 |

- “所有项目的通用底线”被整体列为必读时读取该章全部内容；只列出其中子章节时不需要读取其他子章节。
- 项目类型档案只读取实际命中的档案；无法确定时读取“自动识别与记录”和通用底线，标记待确认，不遍历全部档案猜测。

## 自动识别与记录

- 代理应从依赖清单、锁文件、框架配置、源码入口、构建脚本、容器和部署配置、Schema 或迁移、测试配置、CI 和现有文档识别项目类型。
- 在根 `AGENTS.md` 的“项目事实”中记录：项目类型、主目录档案、必要附加档案、主要目录、权威启动入口、Schema 入口、测试和构建命令。
- 单体全栈、Monorepo、多服务或带批处理任务的项目可以选择一个主档案和多个附加档案，例如“全栈 Monorepo + 数据任务”。
- 框架存在成熟强约定时优先采用框架约定，例如 Django apps、Rails、Next.js App Router、Nuxt、Maven/Gradle、Go packages；但仍必须满足职责唯一、入口唯一、生成物隔离和测试可追溯等通用底线。
- 无法可靠识别时，使用“最小通用档案”，保留已经清晰的结构，并将项目类型、冲突目录或权威入口标记为待确认；不得仅为套模板大规模搬目录。
- 默认早期或单人项目发现重复结构时应直接收敛。存在多人协作、发布包、外部导入路径或部署契约时，先核对影响和迁移方案，再收敛到唯一结构。

## 所有项目的通用底线

### 根目录

- 根目录只放项目级入口和配置，例如 `README.md`、`AGENTS.md`、`.agents/`、依赖与锁文件、构建配置、容器或工作区配置、许可证和必要环境变量样例。
- 源码、测试、文档、迁移、脚本、基础设施和可变运行数据应进入各自目录，不能长期平铺在根目录。
- 不保留 `new`、`old`、`backup`、`copy`、`final`、`v2`、`temp` 等迁移式目录；需要历史回溯使用版本控制。
- 不同时保留承担同一职责的目录，例如 `src/` 与 `source/`、`docs/` 与 `documentation/`、`scripts/` 与 `tools/`。确有不同职责时必须在项目事实或文档中说明。
- 只创建实际需要的目录，不为了满足示例生成空目录、占位模块或无读取方的抽象层。

### 命名与职责

- 顶层通用目录优先使用简短、稳定的小写英文名称；具体包、模块和文件遵循语言及框架约定，不在同一层混用多种命名风格。
- 目录名应表达稳定职责，不使用个人名、日期、阶段名或含糊的 `misc`、`other`、`temp`。
- `common`、`shared`、`utils`、`helpers` 不得成为无边界杂项箱。同一项目只选择必要的共享入口，并按类型、调用方和稳定职责拆分。
- 业务模块按业务域或可独立变化的功能组织；技术层目录只承担明确职责，不能在 controller、service、model 和页面之间复制同一业务规则。
- 一个业务能力只保留一个主实现位置；测试、文档、导出和任务通过正式接口复用，不复制源码形成旁路版本。

### 源码、测试和依赖方向

- 应用源码统一位于所选档案的权威源码根，例如 `src/`、`app/`、`apps/`、`services/` 或框架规定位置；不能多个源码根无规则并存。
- 测试使用一个权威测试根，按源码模块或业务能力可追溯；单元、集成、端到端和契约测试可按规模分层，但不为少量测试建立复杂空结构。
- 测试夹具、Mock 和样例数据集中管理并标明用途；不得复制生产快照、真实密钥或大体量原始文件进仓库。
- 共享模块只能依赖更稳定的基础能力，不得反向依赖具体页面、具体服务入口或部署代码，避免循环依赖。
- 跨应用或跨服务复用达到稳定契约后再进入 `packages/` 或共享库；不因两处代码看起来相似就过早抽象。

### Schema、配置和脚本

- 数据库迁移或 Schema 只保留一个权威目录或框架入口，例如 `migrations/`、`alembic/`、`prisma/`；不得在 `scripts/`、源码和文档中各保留一套建表 SQL。
- 项目配置与代码分离；仓库只保存非敏感默认值、配置结构和环境变量样例，真实密钥进入正式密钥存储或部署环境。
- `scripts/` 只保存开发、构建、发布、迁移、服务管理和一次性受控修复工具，不承担日常业务操作。
- 脚本按职责命名并有调用入口、参数、失败码和文档；任务被页面或正式 API 覆盖后，应删除重复脚本入口。

### 生成物与运行期文件

- 构建产物、依赖缓存、测试覆盖率和框架缓存进入明确目录并加入忽略规则，例如 `dist/`、`build/`、`coverage/`、`.cache/`；不得与源码混放。
- 日志、PID、临时文件、上传、本地缓存、本地数据库、导出和任务输出属于运行期可变内容，应使用一个可配置运行目录或正式外部存储，并加入忽略规则。
- 运行期目录不能成为正式事实来源；需要保留的附件、快照、导出和日志按数据规范进入正式文件存储并建立 manifest。
- 示例、Fixture 和演示资源必须与真实运行数据分开，并明确可提交范围和大小限制。

### 文档与基础设施

- 已建立的正式项目文档统一位于 `docs/`，README 存在时只做入口；具体创建边界和结构遵循 `.agents/api-docs.md`。
- 容器、部署、IaC 和环境编排集中在一个职责明确的位置，例如根级必要配置或 `infra/`、`deploy/` 二选一；不在各业务目录复制同一部署配置。
- 项目只有一个权威服务管理和快速启动入口；目录调整必须同步更新 README、运维文档、容器、CI 和部署引用。
- 不因应用场景规范包或看到推荐结构就机械创建 `README.md`、`knowledge/`、`docs/` 或空标准文档；缺失与创建条件按 `.agents/api-docs.md` 执行。

## 项目类型档案

### A. 文档或规范模板项目

适用于规范、模板、设计资产或文档为主要交付物，没有可运行应用源码的项目。

```text
AGENTS.md
.agents/        # 项目确实需要拆分协作规则时使用
README.md       # 已有或明确需要项目入口时
knowledge/     # 结构化知识、索引和紧密配套的探测或校验工具，按需
docs/          # 正式说明，按需
templates/     # 可复制模板，按需
examples/      # 脱敏示例，按需
scripts/       # 模板校验或生成工具，按需
```

- 不创建空的 `src/`、`tests/`、`backend/` 或 `frontend/`。
- 模板正文、示例和使用说明分开；示例不得成为第二份权威模板。
- 规范或模板项目如需向其他仓库交付规则，应明确维护源、静态交付物、版本和检查入口；目标项目只接收实际需要的一套结果，不复制生成源、构建器或多个候选包。
- `knowledge/` 只在知识本身属于项目交付物时使用；每个知识域保留一个索引，领域内生成、探测和校验工具可以就近放置，但不得保存真实凭据或形成第二份条目汇总。

### B. 单体后端或 API 服务

适用于一个主要部署单元的 API、后台服务或领域应用。

```text
src/<package>/       # 或框架权威源码根
tests/
migrations/          # 或框架权威迁移入口
config/              # 仅非敏感配置结构，按需
scripts/             # 开发与运维工具，按需
docs/
```

- 源码内部按框架和规模选择业务域优先或清晰分层，通常区分入口/API、业务服务、数据访问、领域模型和后台任务。
- 不同时建立 `controllers/`、`handlers/`、`routes/` 三套相同入口，也不同时使用 `services/`、`use_cases/` 承担相同业务逻辑。
- 小型服务保持扁平；只有职责和依赖证据出现后再增加层级。

### C. 前端单页应用或管理后台

适用于 Vue、React、Angular 等独立 Web 前端。

```text
src/
  app/            # 启动、路由、全局 Provider、布局
  pages/          # 或 views/，二选一
  features/       # 可独立变化的业务功能
  shared/         # 稳定公共组件、请求、样式和工具
  assets/
tests/            # 按项目规模选择
public/           # 构建时原样复制的静态文件，按需
docs/
```

- `pages/` 与 `views/` 选择一个；公共组件与业务组件分开，页面不能复制整套公共 CSS、请求和状态逻辑。
- API 客户端、权限、路由、状态、设计变量和错误处理各保留一个公共入口。
- 框架规定 `app/`、`pages/` 或路由目录时采用框架结构，不额外包一层同职责目录。

### D. 全栈单仓或 Monorepo

适用于前端、后端、共享包或多个可部署应用位于同一仓库。

```text
apps/
  web/
  api/
  <other-app>/
packages/
  ui/             # 稳定共享 UI，按需
  shared/         # 稳定共享类型或基础能力，按需
infra/            # 按需
scripts/
docs/
```

- `apps/` 保存可独立运行或部署的应用，`packages/` 保存不能独立作为业务应用运行的共享包。
- 不同时保留 `frontend/`、`backend/` 与 `apps/web`、`apps/api` 两套入口。
- 每个应用的构建、测试和启动命令可独立执行；根工作区提供统一编排，不复制应用内部命令实现。
- 共享包必须有明确调用方和稳定边界，不能把所有跨应用代码放进一个无结构 `common` 包。

### E. 多服务或微服务仓库

适用于多个服务具有独立进程、数据边界或部署周期的仓库。

```text
services/
  <service-a>/
  <service-b>/
packages/         # 稳定共享库，按需
infra/
scripts/
docs/
```

- 每个服务自包含源码、测试、迁移和服务配置；仓库根保存跨服务编排和公共文档。
- 服务不能直接读写其他服务私有表或运行目录；跨服务通过正式契约、事件或共享基础库协作。
- 嵌套 `AGENTS.md` 只记录该服务差异，不能复制根规范。
- 两个服务尚无独立部署、数据或职责边界时，不因未来设想提前拆成微服务。

### F. 库、SDK 或公共组件包

适用于被其他项目依赖而非独立提供业务页面或服务的交付物。

```text
src/
tests/
examples/         # 最小可运行且脱敏
docs/
```

- 公共 API 与内部实现分开；导出入口唯一，避免调用方依赖内部路径。
- 示例只演示正式 API，不复制库实现或保存真实凭据。
- 构建产物由发布流程生成，不与源码同时手工维护。

### G. 数据任务、同步或分析项目

适用于批处理、ETL、同步、报表计算、机器学习或数据分析任务。

```text
src/<package>/
pipelines/        # 编排定义，按需
jobs/             # 可独立调度任务，按需
tests/
migrations/       # 存在数据库时
notebooks/        # 仅探索，按需
docs/
```

- 正式转换和计算逻辑进入可测试源码，不只存在于 Notebook。
- Notebook 不作为生产任务入口；成熟逻辑迁入 `src/`，Notebook 只保留分析说明和小型脱敏样例。
- 原始数据、模型产物、快照和大结果不提交仓库，进入正式数据库或文件存储并建立 manifest。
- `pipelines/` 负责编排，`jobs/` 负责可执行任务，核心业务规则仍进入可复用源码；项目规模不足时可只保留一个。

### H. CLI 或开发工具

适用于面向开发者或运维人员的命令行工具，不适用于应由业务页面触发的日常业务操作。

```text
src/<package>/
  cli/            # 入口与参数解析
  commands/       # 命令实现，按需
tests/
docs/
```

- CLI 入口只负责参数解析、权限检查和调用正式业务服务，不在命令中复制核心逻辑。
- 如果工具逐渐承担业务同步、补跑、分析或导出，应建立正式页面、API 和任务记录，而不是继续扩展旁路命令。

### I. 移动应用

适用于原生 iOS、Android、Flutter、React Native 或其他跨端移动应用。

```text
src/                 # 或框架规定的应用源码根
  app/               # 启动、导航、依赖注入和全局状态
  features/          # 按业务功能组织
  shared/            # 稳定公共 UI、网络、存储和工具
  platform/          # 平台能力适配，按需
assets/
tests/
docs/
```

- 原生双端位于同一仓库时使用 `apps/ios/`、`apps/android/` 和边界明确的共享包，不强行共享平台特有 UI 与生命周期代码。
- 网络、持久化、权限、路由、设计变量和错误处理各保留一个正式入口；页面不自行复制弱网、鉴权或缓存逻辑。
- 构建产物、签名文件、真机日志和本地模拟器数据不进入源码目录；密钥使用平台安全配置和正式发布流程。

### J. 桌面应用或浏览器扩展

适用于 Electron、Tauri、原生桌面应用或浏览器扩展等包含本地能力和前端界面的交付物。

```text
src/
  app/               # UI 与交互
  host/              # 主进程、本地服务或扩展后台
  shared/            # 明确可跨边界复用的类型与逻辑
  bridge/            # IPC 或受控能力桥接
tests/
assets/
docs/
```

- UI、主进程或后台脚本与受控桥接职责分开，不允许页面直接获得不受限制的文件系统、命令或系统权限。
- 浏览器扩展的 background、content script、popup 和 options 使用明确入口及消息契约，不复制权限与存储逻辑。
- 安装包、自动更新、签名、公证和扩展商店产物由发布流程生成，不与源码并列手工维护。

### K. 静态站点或内容型前端

适用于产品介绍、官网、文档站、博客或以静态生成和内容发布为主的项目。

```text
src/                 # 页面、布局和组件，或框架规定目录
content/             # 结构化正文，按需
public/              # 原样复制的公开静态资源
assets/              # 参与构建优化的资源，按需
tests/
docs/
```

- 页面模板、内容数据和媒体资产职责分开；不把大量正文硬编码进通用组件，也不同时维护 `content/` 与另一套同职责内容目录。
- 静态生成、预览和发布只有一套权威命令；生成目录不提交为第二份源码，除非托管平台明确要求并有自动发布证据。
- 内容量或审核流程增长后应采用正式内容模型和发布入口，不通过复制页面文件维持栏目与版本。

### L. 基础设施即代码或平台自动化项目

适用于 Terraform、Ansible、Helm、Kubernetes、云资源、环境编排或运维自动化为主要交付物的项目。

```text
modules/             # 可复用基础设施模块，按需
environments/        # 环境组合与非敏感参数
policies/            # 安全或合规策略，按需
scripts/             # 受控辅助工具，按需
tests/
docs/
```

- 环境目录只保存组合与非敏感差异，不复制完整模块；状态文件、计划结果、密钥和真实清单不提交仓库。
- 模块输入、输出、版本和依赖明确，生产变更通过计划、评审、应用和回滚流程，不以手工控制台修改作为第二主路径。
- 集群清单、Helm、Terraform 与脚本职责不重叠；同一资源只有一个权威声明和一个状态管理入口。

### M. 嵌入式或固件项目

适用于 MCU、设备固件、边缘运行时和硬件相关软件。

```text
src/
include/             # 语言或工具链需要时
boards/              # 板型与硬件差异，按需
drivers/             # 设备驱动，按需
tests/               # 主机侧、模拟器或硬件测试
tools/               # 构建、烧录和诊断工具，按需
docs/
```

- 硬件差异集中在板级配置或驱动边界，不在业务模块散落条件编译和型号判断。
- 构建、烧录、升级和诊断入口明确区分；固件镜像、符号文件、设备日志和采集数据进入构建或外部存储目录。
- 第三方驱动、生成代码和手写代码边界清楚；生成目录不得成为人工修改的第二份实现。

## 结构调整与迁移

- 调整前列出当前目录职责、目标档案、重复入口、导入路径、启动与构建引用、测试发现、部署和外部调用影响。
- 早期项目应在一个改动中完成移动、引用更新、旧目录删除、测试和文档同步，不长期保留新旧两套目录。
- 不使用软链接、路径别名、复制文件、转发模块或旧包壳作为默认兼容；存在明确外部契约时按用户确认的期限短期保留并记录下线计划。
- 移动后检查源码导入、动态加载、静态资源、模板、迁移、容器构建上下文、CI 缓存、发布包清单和文档链接。
- 仅当目录调整带来明确职责收敛、入口统一或维护收益时实施；不为视觉整齐进行大范围无收益重排。
