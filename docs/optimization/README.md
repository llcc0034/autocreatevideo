## 维护与对账口径

- `记录日期`表示首次登记日期，`最近核对`表示最后一次按当前代码、页面、API、迁移和测试重新判断状态的日期。
- 最近一次整体对账基线为 2026-09-04，Django migration head 为 `0136_allow_unresolved_comfy_contract_hashes`。后续迁移或主路径变化后必须重新核对受影响项。
- v3、v4、v6、任务 ID、主机状态和本地数据库数量等易变化事实只放在“历史证据”或注明日期的只读快照中；稳定的“当前现状”使用能力合同描述，不追逐最新版本号。
- 已落地基础与剩余缺口分开记录。测试漂移、意外不可逆迁移或当前合同回归属于交付缺陷，不能提前标记完成；用户已授权的物理清理可以明确不可逆，不为恢复已删历史/审计增加逆转换。
- 2026-09-06最新清理口径：不为旧代码、旧口径、历史或审计数据开发兼容层；不兼容对象及其核定依赖可物理删除。旧条目的“历史必须保留/另行确认审计删除”决策已被替代，实际清理边界以统一计划第1.5、11、21节为准。保留台账决策文字不意味着需要保留相应业务数据或旧解析代码。

## 状态说明

- `待优化`：问题已确认并记录，尚未开始实施。
- `实施中`：方案已部分落地或有明确改动在进行，但剩余范围尚未完成全部验收。
- `已完成`：实现、迁移、测试、页面、API 与正式文档已一起收敛并通过验收。
- `观察中`：暂不改动，等待触发条件或更多运行证据。
- `暂不做`：已评估但当前明确不进入实现。

## 价值判断说明

- `必须完成`：涉及安全、数据真实性、迁移、正式检查或自动生产准入，缺口会直接破坏主路径可信度。
- `值得实施`：已有明确用户价值且方案能复用现有事实源；按优先级排期，不代表已经进入开发。
- `条件触发`：当前主路径可以工作，只有规模、频率、外部分发或无人值守需求达到明确阈值后才值得投入。
- `不再实施`：原方案会形成第二主路径、第二事实源或投入明显大于收益；保留决策记录，后续只在出现新事实时重新评估。
- `已兑现`：价值已随已完成实现交付；后续只做回归和运行观察。

## 建议投入顺序（2026-09-04）

以下为历史批次顺序；当前投入顺序以[详细计划](execution-instance-unification-plan.md)第9、10节为准。合同正确性及数据/权限/费用底线保留；完整容量认证不再作为本轮可用主链的前置，按第17节显式策略处理。

2026-09-04 批次的 17 项评估结果为：3 项价值已兑现、2 项必须完成、7 项值得实施、4 项条件触发、1 项不再实施；该批次统计不含后续单独登记项。不是所有待办都值得立即做，状态与优先级不能替代价值判断和触发条件。

1. 先完成 `OPT-CONTRACT-001`，恢复正式迁移与回归基线的可信度；这是其他功能交付的前置条件。
2. 将 `OPT-CAPACITY-001` 作为自动生产安全 P0 推进；在完成前，不把小 Smoke 外推为大请求容量认证。
3. 先联动完成 `OPT-WORKFLOW-IMPORT-001` 与 `OPT-WORKFLOW-PROJECTOR-001`，恢复 ComfyUI saved workflow 从来源纳管到可执行准入的清晰主路径；候选纳管不能替代真实 Smoke。
4. 优先处理范围较小且能消除错误阻断的 `OPT-RECIPE-UI-001`，随后补齐 `OPT-SMOKE-UI-001` 的逐 operation 矩阵。
5. 再按产品使用量推进 `OPT-ROUTING-001`、`OPT-REF2VA-001` 与 `OPT-RELATION-001`；三项分别改善配方作者体验、动态参考匹配和复杂实体语义。
6. `OPT-LOCAL-RUNTIME-001`、`OPT-REF2VA-002`、`OPT-DIST-001` 与 `OPT-NORMALIZE-001` 只在表格所列触发条件出现后投入；没有新证据时不抢占 P0/P1。
7. `OPT-MANUAL-001` 原方案不再投入；如人工体验仍有痛点，只在 ProductionRun 主链内登记独立 UI 优化。

## OPT-SMOKE-UI-001 Deployment Smoke 按 operation 补齐集中覆盖矩阵

### 已落地基础

- 一个文本 Deployment 可以声明并烟测多个 operation，例如 `script.generate`、`script.structure`、`prompt.normalize` 和 `visual_rules.generate`。
- 一级“验收与烟测中心”和集中只读 API 已上线；服务端已按 Deployment + operation 返回适用性、`fresh_passed_snapshot`、`latest_attempt` 与唯一动作入口。
- Deployment 或模型实例卡继续只突出最近一条持久任务；完整能力覆盖由集中页和按 operation 的服务端证据解释，不根据最近任务反推。
- Smoke attempt 与新鲜通过快照按 operation 独立保留，生产准入继续读取同一持久证据；重新执行某一项不会覆盖其他 operation 的服务端事实。

### 剩余缺口与方案

1. 集中页目前仍把多个 operation 压缩为一条聚合状态、能力名列表和“最新尝试”摘要；继续以现有集中 API 为唯一投影入口，并在 operation 行补充 `latest_snapshot`/历史证据摘要，或明确关联现有 Deployment evidence API。不得创建第二套证据或提交入口。
2. 矩阵把证据新鲜度与任务状态分开：证据列显示 `fresh`、`expired`、`not_run` 或 `historical`；最新 Attempt 列显示真实的 `queued`、`submitting`、`submitted`、`cancel_requested`、`succeeded`、`failed`、`cancelled` 或 `uncertain`。
3. 每行显示最近证据时间、到期时间、最新 Attempt ID 与状态；不能仅因 `fresh_passed_snapshot` 为空就猜测“过期”或“从未执行”。
4. 行内进入现有实例 Smoke 动作或只读 Attempt 详情；完整历史继续读取已有按 Deployment + operation 过滤的 attempt API。
5. “最近一次烟测任务”和“全部 operation 覆盖矩阵”使用不同标题，避免把一条任务误认为部署的完整能力。

### 剩余验收条件

- 同一 Deployment 连续执行三个不同 operation 后，页面同时显示三项各自的最新状态和新鲜度。
- 已过期证据明确显示“已过期”，不能仅以“成功”颜色伪装为当前可用。
- 从矩阵进入的任务详情与服务端任务 operation、状态、时间和证据一致。
- 组件与浏览器验收覆盖多 operation、单项重跑、过期、失败和不确定状态；单项变化不影响其他行。

## OPT-RECIPE-UI-001 配方路由编辑器解耦无关能力目录并显示真实错误

### 当前根因

- Recipe 编辑器已经拥有独立的阶段、审批、路由和预设目录，但路由变体上限仍来自完整 `ProductionCapability`，而不是自己的 options 合同。

- 空 conditioning mode 不必然表示某条 Recipe route 无效；不能为修复编辑器而放宽 ProductionRun 与 SeriesStudio 对完整 ProductionCapability 的失败关闭。

### 目标方案

1. 在 `ProductionRecipeEditorOptions` 增加独立 `effective_limits`，至少包含 `max_variants` 与 `max_routing_routes`。
2. Settings 的 Recipe 编辑器只消费该子合同；完整生产能力、Recipe 依赖目录和 Recipe options 分别保留错误，不互相覆盖。
3. options limit 缺失或非法时只阻断受影响的路由控件并显示真实字段错误；其他 Settings 分区不因无关目录失败而伪装缺少数据。
4. 同步更新 OpenAPI、服务端 Serializer、前端类型与适配器，并删除把当前耦合误认为正确合同的旧测试口径。

### 验收条件

- 完整生产能力因空 conditioning modes 失败时，ProductionRun 继续失败关闭，但 Recipe 编辑器仍能使用自身合同中的真实上限。
- 服务端修改 Recipe limit 后页面同步变化，前端没有静态上限或从其他能力目录拼接的回退值。
- 回归覆盖空 modes、options 读取失败、limit 缺失或非法、真实 limit 变化及错误隔离。

## OPT-CAPACITY-001 主机容量证据包 / Certified execution envelope

2026-09-06当前决定：用户要求先打通可用主链。本项拆为首期规格观测/可配置告警（并入统一计划）与后续完整envelope认证。以下保留当轮证据文字，不要求保存不兼容数据库记录；原“全部容量认证必须先完成”的P0排期已替代。目标准入只以[统一计划1.3](execution-instance-unification-plan.md)第17节为准，尚未调整真实配置。

### 已落地基础

- `RuntimeHost → HostCapabilitySnapshot → RuntimeModelAvailability` 已持久化主机硬件、快照 TTL、详情 hash 与精确模型文件 size/hash；主机 Probe 生成可审计快照。
- ProductionRun 已冻结 `execution_capacity`：绑定主机快照、配置与物理并发上限、兼容并发和超时；worker 在领取和提交前复核容量 hash、当前主机、快照完整性与并发。
- Production Readiness 已检查精确 Workflow、真实 Smoke、主机快照和模型文件证明；`uncertain`、稳定 submission token、不自动重新 POST 与版本化 `execution_monitoring` 已有独立权威合同。
- 上述基础能证明“主机、文件、并发和执行合同完整”，但不能证明“当前请求的宽高、帧数、素材组合与 steps 落在实测范围内”。

### 尚未完成的容量认证能力

- 当前没有 `CertifiedExecutionEnvelope` 模型、API、标准 Schema 或覆盖匹配器。
- 容量冻结尚不接收并比较本次宽高/像素、帧率、帧数/时长、steps、conditioning mode、音频模式、输入槽基数、参考视频有效帧及提示词长度桶。
- 较小 fixture 因而仍可能让更大的生产请求进入高成本队列，在采样前 OOM、长时间无有效进度或使原生进程退出。
- 不能用模型名、固定帧数或单一 Workflow 特例修补；否则新模型、新节点或低显存实现仍需修改核心路由。

### 历史证据（2026-08-26）

- 当时 H3 Workflow v3 的成功 Smoke 样本为 352×608、22 帧、4 steps、1 条参考视频；请求扩大为 124 帧、3 张参考图、1 条动态视频、长提示词与原生音频后，四个样本为 0/4 通过。
- 该案例只证明“小 Smoke 不能外推大请求”的通用缺口，不代表当前 Workflow 版本、当前主机状态或已经认证的硬件下限。

### 后续完整认证方案（不阻塞首期可用主链）

1. 由成功的真实 Smoke 派生不可变、模型无关的容量认证事实；人工只能发起、审核或退役，不能手填“通过”。
2. 每份 envelope 绑定 RuntimeHost、新鲜 HostCapabilitySnapshot、精确 Deployment/Workflow target hash、模型文件 hash、驱动与运行时版本、启动参数及 Smoke attempt。
3. 从 Workflow/Deployment 的结构化合同投影通用请求维度：输出媒体、宽高/像素、帧率、帧数/时长、steps、conditioning mode、音频模式、输入槽媒体类型与基数、参考视频有效帧及提示词长度桶。
4. Smoke 补录执行耗时、最长有效静默、峰值显存/RAM、远端终态和 FFprobe/文件探测结果；Provider 不支持的指标明确为 `unavailable`，不能伪造。
5. ProductionRun 选路和 worker 提交前调用同一覆盖匹配器；超出范围时列出具体未覆盖维度，不静默降参、删素材或换模型。
6. 在现有“验收与烟测中心”展示容量认证，不再建立独立 Smoke 入口；Workflow 发布与容量认证继续是两个独立事实。
7. envelope 可记录实测最长静默作为认证证据，但不取代现有 `execution_monitoring`、硬截止时间、`uncertain` 和不重放合同。

### 首期操作口径与后续收紧

统一实例合同按1.3落地后：

1. 只把真实 Smoke 的精确分辨率、帧数、素材槽组合、运行配置和主机视为已验证样本，不向外推断更大请求。
2. 超出/未知样本默认显示容量警告，在硬合同、原资源并发和费用授权内执行；管理员启用require_evidence才按覆盖阻断。不为每种token长度强制补测，不把放行伪装为已认证，也不手填未经测试的最低显存。
3. 任一 OOM、idle 误杀或 native abort 都保留原 Attempt，并沿现有 uncertain/失败合同核对远端终态；恢复后创建新 Attempt，不自动重放旧提交。

### 后续完整认证的严格模式验收

- 新模型或新工作流能只通过结构化能力合同、系统设置和 real smoke 建立 envelope，无需修改核心路由源码。
- require_evidence下，22帧/少素材样本不能授权124帧/多素材；warn下允许硬合同内请求但明确显示未覆盖。两者不改变真实样本内容。
- RuntimeHost、运行时版本、模型hash、工作流合同、启动参数或能力快照漂移后旧envelope不再显示有效；执行身份漂移仍阻断，单纯容量证据失效是否阻断由统一策略决定。
- 并发请求、参考视频帧数、原生音频和提示词长度桶均进入覆盖判定，并有边界、漂移和伪造值回归测试。
- 容量覆盖失败沿现有可审计的不确定/失败状态处理，不重复提交；恢复后必须创建新的 Attempt 和新的容量证据。
- 系统设置、Readiness、任务详情和运维指南以中英双语显示已覆盖范围、缺失维度、证据时间与失效原因。

### 本次不代表

- 本条记录不表示 certified execution envelope 已实现，也不改变现有 Workflow、Deployment 或任务状态。
- 任一历史小样本都不能替代完整请求验收；更大显存主机与 DynamicVRAM headroom 的最低安全值仍待真实测试。
- 本方案不允许用自动降参、删除参考素材或改用其他生成模式伪装请求成功。

## OPT-RELATION-001 Bible 实体所有权与附着关系合同

### 当前合同缺口

- Bible、Shot 与逐镜参考绑定目前只保存实体和素材，没有结构化保存 `attached_to`、`worn_by`、`held_by`、`part_of`、`inside` 或 `located_in` 等关系。
- 该问题会增加低分辨率、低 steps 条件下的特征串位风险，属于视觉语义质量告警；不否定任务、媒体探测、引用顺序和发布链路已经成功的技术事实。

### 历史证据（2026-08-28）

- v23 实测中，人物参考图已经包含胸前徽章，同时又提交了独立徽章参考图；徽章与种荚均以普通 Prop 进入 Ref2VA。
- 实际槽位顺序正确，但“徽章固定在人物胸前、种荚是另一独立道具”只存在于自然语言，不能被主链路冻结、校验或用于合并参考锚点。

### 当前操作口径

1. 固定佩戴且不独立参与剧情的徽章、胸针、纹章等优先并入人物 `visual_identity`，由人物参考图承担唯一视觉锚点。
2. 人物参考图已清楚包含固定附件时，不再额外提交同一附件的独立参考图；需要摘下、传递、操作或单独影响剧情时才保留独立 Prop。
3. 提示词明确写出附件所有者、固定位置和不同道具特征不得互相转移，但这些文字只作为质量约束，不能冒充结构化关系事实。
4. 缺少可推断关系、重复锚点或可能的特征迁移默认进入告警与人工成片审核，不阻断主流程。

### 目标方案

新增模型无关、版本化并参与冻结哈希的 `EntityRelation` 合同，关系至少包含源实体、受控 predicate、目标实体以及 attachment site、persistence、reference strategy 等限定信息。关系沿 `Bible 候选与审核 → Bible → Shot 快照 → reference binding 投影 → PromptArtifact → Workflow 审计` 传递；`inherit_owner_anchor` 可在所有者图片已经包含附件时稳定省略重复图片槽位。

关系类型、允许的实体组合、基数、持续性、引用策略、提示词投影位置与告警等级进入系统配置；核心代码只实现通用关系校验、冻结、投影和工作流 adapter，不识别具体模型或“徽章”等业务词。

### 阻断边界

- 关系引用不存在、跨项目、predicate 未注册、固定附件同时绑定互斥所有者，或冻结关系与 PromptArtifact/Workflow hash 漂移时硬阻断。
- 文本疑似包含关系但未结构化、所有者图片与附件图片形成重复锚点、多个 Prop 有特征迁移风险，或最终成片疑似串位时默认只告警并继续，交由人工判断是否调整策略。
